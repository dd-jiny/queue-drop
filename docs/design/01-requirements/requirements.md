## 1. 서비스 개요

**쉬운 설명**
> 한정판 상품을 "먼저 온 순서대로 응모 자격을 주고, 응모자 중에서 추첨"하는 서비스예요.
> 오픈 순간 사람이 몰리면 줄(대기열)을 세워 조금씩 들여보내고, 정해진 인원이 차면 응모를 마감해요.
> 마감 시각이 되면 자동으로 당첨자를 뽑아요. 결제는 없어요.

**해결하려는 문제**
| 관점 | 문제 |
|------|------|
| 사용자 | 오픈 순간 트래픽 폭주 속에서도 **먼저 온 사람이 먼저 기회를 얻는 공정성** |
| 비즈니스 | 응모 정원·쿠폰 수량을 **절대 초과하지 않는 정합성** (오버 응모 / 오버 발급 방지) |
| 시스템 | 짧은 순간 집중되는 쓰기 요청을 흡수하면서 **여러 서비스에 걸쳐 상태 일관성 유지** |

**범위 밖 (Out of Scope)**
- 결제, 배송, 구매 확정
- 당첨 후 별도 "구매 신청" 단계 (응모 = 신청)
- 쿠폰 사용처 (쿠폰은 발급·보유 조회까지만)

## 2. 용어 정의

| 용어 | 정의 |
|------|------|
| 상품 (Product) | 한정판 상품 자체의 정보 |
| 드로우 (Drop) | 특정 상품에 대한 1회의 응모·추첨 이벤트. 응모 정원 M, 당첨 수량 K, 오픈 시각, 응모 마감 시각을 가짐 |
| 대기열 (Waiting Queue) | 드로우별로 존재하는 응모 진입 대기 줄 |
| 입장 토큰 (Entry Token) | 대기열을 통과한 사용자에게 발급되는 일정 시간 유효한 응모 자격 |
| 응모 (Entry) | 입장 토큰을 가진 사용자가 드로우에 참여하는 행위. 선착순 M명까지 접수 |
| 추첨 (Draw) | 응모 마감 시각에 응모자 M명 중 K명을 무작위로 당첨 처리 |
| 쿠폰 이벤트 (Coupon Event) | 드로우와 무관한 독립 선착순 쿠폰 발급 이벤트 |

## 3. 액터

| 액터 | 설명 |
|------|------|
| 사용자 | 회원가입·로그인, 대기열 진입, 응모, 쿠폰 발급, 랭킹 조회 |
| 관리자 | 상품·드로우·쿠폰 이벤트 등록 (계정은 REQ-USER-04 로 생성) |
| 스케줄러 (시스템) | 대기열 입장 처리, 응모 마감 시각 자동 추첨 |

## 4. 기능 요구사항

### 4.1 회원 (user-service)
| ID | 요구사항 |
|----|----------|
| REQ-USER-01 | 사용자는 회원가입할 수 있다 |
| REQ-USER-02 | 사용자는 로그인하여 JWT 를 발급받는다 |
| REQ-USER-03 | JWT 검증은 Gateway 에서 수행하고, 검증된 userId 를 헤더로 내부 서비스에 전달한다 |
| REQ-USER-04 | 관리자 계정은 user-service 기동 시 환경변수(`ADMIN_EMAIL`, `ADMIN_PASSWORD`)로 생성한다. 해당 이메일 계정이 없을 때만 생성하며, 회원가입 API 는 USER 만 만든다 |

### 4.2 상품·드로우 (product-service)
| ID | 요구사항 |
|----|----------|
| REQ-DROP-01 | 관리자는 상품을 등록할 수 있다 |
| REQ-DROP-02 | 관리자는 상품에 대한 드로우를 등록한다 (응모 정원 M, 당첨 수량 K, 오픈 시각, 응모 마감 시각). 제약: M ≥ K |
| REQ-DROP-03 | 사용자는 드로우 목록·상세(상태 포함)를 조회할 수 있다 |

### 4.3 대기열 (queue-service) — 핵심 기능 ①
| ID | 요구사항 |
|----|----------|
| REQ-QUEUE-01 | 대기열은 **드로우별**로 존재한다 |
| REQ-QUEUE-02 | 사용자는 드로우 오픈 이후 대기열에 진입하며, 진입 순서대로 순번이 매겨진다 |
| REQ-QUEUE-03 | 사용자는 자신의 현재 대기 순번("내 앞에 N명")을 조회할 수 있다 |
| REQ-QUEUE-04 | 스케줄러는 **주기적으로(예: 1초) 앞에서부터 N명**에게 입장 토큰을 발급한다 |
| REQ-QUEUE-05 | 입장 토큰은 **TTL(예: 5분)** 후 만료된다 |
| REQ-QUEUE-06 | 응모 API 는 유효한 입장 토큰이 있어야 호출할 수 있다 |

### 4.4 응모·추첨 (entry-service)
| ID | 요구사항 |
|----|----------|
| REQ-ENTRY-01 | 사용자는 입장 토큰으로 드로우에 응모한다 |
| REQ-ENTRY-02 | 응모는 **선착순 M명**까지만 접수되며, 정원이 차면 응모가 마감된다 |
| REQ-ENTRY-03 | **1인 1드로우 1응모**. 중복 응모는 거부한다 |
| REQ-ENTRY-04 | 응모는 **취소할 수 없다** |
| REQ-ENTRY-05 | **응모 마감 시각에 자동으로** 응모자 중 K명을 무작위 추첨한다 (정원이 일찍 차도 마감 시각까지 대기) |
| REQ-ENTRY-06 | 사용자는 자신의 응모 내역과 당첨/낙첨 결과를 조회할 수 있다 |

### 4.5 선착순 쿠폰 (coupon-service) — 핵심 기능 ②
| ID | 요구사항 |
|----|----------|
| REQ-COUPON-01 | 관리자는 쿠폰 이벤트를 등록한다 (총 수량, 발급 시작 시각) |
| REQ-COUPON-02 | 사용자는 발급 시작 이후 쿠폰 발급을 요청한다. 총 수량까지 선착순 발급 |
| REQ-COUPON-03 | **1인 1매**. 중복 발급은 거부한다 |
| REQ-COUPON-04 | 사용자는 보유 쿠폰을 조회할 수 있다 |
| REQ-COUPON-05 | 쿠폰 발급은 대기열을 거치지 않는다 |

### 4.6 랭킹 (ranking-service) — 핵심 기능 ③
| ID | 요구사항 |
|----|----------|
| REQ-RANK-01 | **인기 드로우 랭킹**: 드로우별 응모 수 기준 실시간 순위 |
| REQ-RANK-02 | **유저 활동 랭킹**: 응모 1회 = 1점, **주간(매주 리셋)** 과 **전체 누적** 두 가지 |
| REQ-RANK-03 | 랭킹은 응모 이벤트를 비동기로 소비하여 집계한다 |

## 5. 비기능 요구사항 (방향 합의 필요)

> 여러 기능에 걸친 결정이므로 별도 문서에 합의 내용을 기록한다 → [concurrency-consistency.md](../04-non-functional/concurrency-consistency.md)

| ID | 요구사항 | 상태 |
|----|----------|------|
| NFR-01 | 응모 정원 M / 쿠폰 수량은 동시 요청 상황에서도 **절대 초과되지 않는다** | 합의: Redis Lua 원자 판정 (D1) |
| NFR-02 | 중복 응모 / 중복 발급은 동시 요청 상황에서도 발생하지 않는다 | 합의: Lua Set 검사 + DB UNIQUE (D1) |
| NFR-03 | Redis·Kafka·DB 간 상태 불일치 발생 시 복구 가능해야 한다 | 합의: 발행 확인·보상 (D2), 추첨 전 건수 일치 대기 (D6) |
| NFR-04 | 추첨은 공정해야 하고 결과를 재현·검증할 수 있어야 한다 | 합의: 시드 저장 셔플 (D7) |

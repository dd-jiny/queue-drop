**측정 규칙**
- 요약 통계는 `--summary-trend-stats "avg,min,med,max,p(90),p(95),p(99)"`.
- **워밍업 후 측정**: 서비스·gateway 재시작 직후에는 JIT 가 덜 끝나 같은 요청이 크게 느리다(4장 참고). 시나리오마다 작은 워밍업 실행 1회 후 측정한다. "1차(개선 전)" 수치는 이 규칙을 정하기 전, 기동 직후 측정이다.
- 정합성은 k6 직후(마감 전) `verify-drop.sh <id> --expect <entry_ok>` / `verify-coupon.sh <id> --expect <n>`, 마감 후 `verify-drop.sh <id> --after-draw`.
- 서버 측 지표는 Prometheus(`http.server.requests`, Hikari, consumer lag, 커스텀 outcome·compensated·admitted).

## 3. 병목 분석

### B1. gateway → 서비스 연결 폭주로 accept 큐 초과 (S2 로그인, S3 쿠폰)
- **관찰**: 5,000명 동시 로그인 중 gateway 로그 `Connection reset` 647건 → 500. 쿠폰 4,000 동시 요청에서도 동일.
- **근거**: user-service 컨테이너 `/proc/net/netstat` — `ListenOverflows` 7,745, `SyncookiesFailed` **647 (실패 수와 정확히 일치)**. coupon-service `ListenOverflows` 1,042.
- **원인**: Spring Cloud Gateway 의 업스트림 풀 기본값이 ELASTIC(상한 없음)이라 동시 요청 수만큼 새 TCP 연결을 연다. 서비스 Tomcat 의 accept 큐(`accept-count` 기본 100)가 넘쳐 SYN cookie 검증 실패 → RST.
- **조치 (P1)**: gateway 풀 FIXED, 서비스당 200 연결(대기 큐 무제한, 대기 30초 초과 시 500), 서비스 `accept-count` 1024.

### B2. gateway OOM kill (S3)
- **관찰**: 쿠폰 4,000 동시 요청 직후 gateway 컨테이너 재기동(RestartCount 1), k6 는 전 요청 EOF·connection reset.
- **근거**: `docker stats` 에서 gateway 메모리 696MiB(로그인 직후) → 761.8/768MiB 정체 → 재기동 후 319MiB.
- **원인**: `MaxRAMPercentage=75` 로 힙 576MB, 나머지 192MB 에 Netty 다이렉트 버퍼(클라이언트 연결 4,000 + 업스트림 연결)·메타스페이스·스레드 스택이 들어가지 못함.
- **조치 (P2)**: gateway 만 메모리 1024m, 힙 50%(512m), 다이렉트 256m. 이후 모든 실행에서 재시작 0, 최대 656MiB.

### B3. 로그인이 BCrypt 동안 DB 커넥션 점유 (모든 시나리오의 준비 단계)
- **관찰**: 3,000명 로그인 중 `hikaricp_connections_pending` 최대 189, active 10(풀 전부).
- **원인**: `UserService.login` 의 `@Transactional(readOnly=true)` 가 BCrypt 비교(약 50ms CPU) 동안 커넥션을 쥠.
- **조치 (P3)**: 트랜잭션 제거 → pending 0, active 최대 2. 로그인 p99 는 3.35s → 2.92s 로 조금만 줄었다 — 상한은 CPU(BCrypt, user-service CPU 사용률 98%)다.

### B4. 콜드 스타트 (JIT 워밍업) — 쿠폰 지연의 주원인
- **관찰**: P1·P2 이후에도 쿠폰 p99 834ms, 그런데 coupon-service 서버 측 최대 처리 시간은 176~330ms, 가장 빠른 요청도 300ms 이상.
- **분리 실험** (4,000 VU, 0.5초 jitter 버스트, 호스트 k6):

| 대상 | p50 / p99 (ms) | 해석 |
|------|----------------|------|
| gateway `/actuator/health` (업스트림 없음) | 1.2 / 11.6 | 포트 포워딩·gateway 수신은 병목 아님 |
| `GET /api/rankings/drops` (JWT 검증 + 업스트림 + Redis) | 18.8 / 50.0 | gateway 라우팅 경로도 병목 아님 |
| `POST .../issue` 매진 이벤트 (Lua 판정만, Kafka 없음), coupon 재기동 직후 1~4회 | 400 / 577 → 112 / 187 → 23 / 72 → 3 / 19 | **반복할수록 빨라짐 = JIT** |
| 같은 요청, 예외 WARN 로그 끔, 재기동 직후 1~2회 | 361 / 448 → 81 / 156 | 로그가 원인이 아님 |

- **기각한 가설**: ① Tomcat 스레드 200 대기 → 가상 스레드(`spring.threads.virtual.enabled`)로 바꿔도 p99 851ms(콜드)로 개선 없음. ② 예외 응답마다 남기는 WARN 로그의 동기 출력 → 로그를 꺼도 콜드 상태는 동일. ③ gateway 풀 크기 → 워밍업 후 200 과 1000 차이 없음(p99 160~204 vs 153~274ms).
- **결론**: 드로우 오픈·쿠폰 시작처럼 **트래픽이 0 에서 순간적으로 치솟는 서비스는 첫 버스트가 콜드 JVM 에 떨어지면 지연이 3~5배**가 된다. 운영 대응은 배포 직후 워밍업 트래픽, 오픈 전 사전 요청, 또는 CDS/AOT 캐시(백로그).

### B5. 서비스 컨테이너 OOM (쿠폰 14,000 동시)
- **관찰**: X5 직후 coupon-service RSS 757/768MiB 에서 정체, 다음 버스트(가상 스레드 실험 워밍업)에서 재기동(RestartCount 1).
- **근거**: JVM 힙 사용 최대 176MB / 최대 576MB, 비힙 163MB, 스레드 최대 239. G1 이 커밋한 힙을 바로 돌려주지 않아 RSS = 커밋 힙 + 비힙 + 스레드·네이티브가 한도를 넘음.
- **조치 (P4)**: 공용 Dockerfile `MaxRAMPercentage` 75 → 50 (힙 384MB, 실사용의 2배). 이후 재시작 0, coupon RSS 최대 644MiB, GC 최대 정지 13ms.
- **남은 위험**: gateway 는 15,000 동시에서 954/1024MiB 까지 올랐다 → 백로그(gateway 메모리·동시 연결 상한).

### B6. 단일 인스턴스 처리량 상한 (쿠폰 10,000 동시 이상)
- **관찰**: 11,000~15,000 동시 발급 요청에서 클라이언트 p99 0.7~1.2s. 같은 요청의 평시 서버 처리 시간은 1~3ms(워밍업 후 프로브)인데, 버스트 중에는 서버 측 평균 11~18ms·p99 33~78ms 로 늘었다.
- **상태별 분리** (Prometheus `http.server.requests`, 버스트 45초 구간):

| 실행 | 202 (Lua + Kafka ack) 평균 / p99 | 409 (Lua 만, Kafka 없음) 평균 / p99 | 건수 202 / 409 |
|------|----------------------------------|-------------------------------------|----------------|
| X3 | 18.3 / 77.2ms | 12.8 / 49.5ms | 2,475 / 9,900 |
| X5 | 11.3 / 33.1ms | 11.5 / 35.6ms | 3,600 / 13,275 |
| X3 (P4 후) | 16.2 / 55.6ms | 18.4 / 53.4ms | 2,475 / 9,900 |

- **해석**: Kafka 를 거치지 않는 409 도 202 와 같은 수준으로 느려진다 → **"Kafka 동기 대기가 스레드를 묶는다" 는 처음 가설은 주원인이 아니다**. 경로 공통 구간(Redis Lua 호출 — 서비스당 Lettuce 공유 연결 1개로 직렬화, 요청 스레드 200·CPU 경합, gateway 앞단 대기)이 후보이며 이번 측정으로 하나로 좁히지 못했다. 서비스 앞단(gateway 풀 200·Tomcat 스레드 200)에서의 대기는 서버 측 타이머에 잡히지 않으므로, 클라이언트 p99 와 서버 p99 의 차이(약 0.6~1.1s)가 앞단 대기다.
- **다음 확인 방법**: Lettuce 명령 지연(`lettuce.command.*` 메트릭 활성화), Redis `INFO commandstats`·`SLOWLOG`, coupon-service 를 2개로 늘린 같은 버스트 비교. 개선 선택지는 백로그 E-56 (수평 확장 / 가상 스레드 + 풀 확대(미검증) / 매진 이후 경로 단축 / 비동기 발행(D2 변경, 사용자 결정)).

### 관찰 — 로그인 처리량 상한 (확대 규모에서 드러남)
- BCrypt(strength 10) 로그인은 15코어 VM 에서 초당 약 235건이 상한(user-service CPU 98%).
- 10,000명이 한꺼번에 로그인하면 약 42초가 걸리고, gateway 풀 대기 30초를 넘긴 2,670건이 `PoolAcquireTimeoutException` → **500** (5장 X1-1차). 이 경우 의미상 503(과부하, 재시도 가능)이 맞다 → 백로그.
- 실제 사용자는 오픈 전 시간에 나눠 로그인하므로 확대 측정은 `LOGIN_SPREAD_SEC` 로 로그인을 분산했다.

- **정합성은 모든 확대 실행에서 PASS** (초과·중복 0, Redis = DB = 랭킹, 추첨 결과 일치, lag 은 k6 종료 직후 0).
- **응모 API 는 초당 1,000건 입장에서도 서버 측 p99 7.6ms** (entry-service `http.server.requests`). 클라이언트 측 p99 167ms 와의 차이는 gateway·포트 포워딩 구간.
- **`ENTRY_SOLD_OUT` 427 / 518**: 입장 배치(1,000)가 남은 정원으로 잘리지 않아 마지막 배치에서 남은 자리보다 많이 입장시키고, 응모 판정(Lua)이 초과분을 거절한다. 정합성은 판정이 지키므로 문제없지만, 사용자는 "입장했는데 매진" 을 본다. 이는 사용자 결정 E-34("주기당 N명 유지, 잔여와 무관 — 8단계에서 소진 직전 SOLD_OUT 수 관찰")의 관찰 결과다: 배치 100 에서는 0건(S1, X1), 배치 1,000 에서는 427·518건.
- **queue_enter p99 443~506ms (X2·X4)**: queue-service 서버 측 p99 는 최대 69ms. 직전에 queue-service·gateway 를 재기동했고 워밍업이 2,000명 1회뿐이었다. 충분히 데운 X1(같은 10,000 동시 진입)은 43ms.

## 6. 결론
- **정원·수량 초과 0, 중복 0** — 기본 규모 S1~S6 과 확대 규모(드로우 최대 16,294명 참여 / 쿠폰 최대 15,000 동시) **모든 실행**에서 `verify-drop.sh`·`verify-coupon.sh` PASS. 1차 측정에서 gateway 가 죽고 요청 4,000건이 실패했을 때도 Redis·DB 는 일치했다. 보상(`COMPENSATED`·`NOT_OURS`)은 측정 전 구간에서 0.
- **설계 결정의 효과**
  - D1 Redis Lua 판정: 정원·수량·중복을 원자적으로 지켰다. 응모 판정의 서버 측 p99 는 초당 1,000건 입장에서도 8ms 안쪽.
  - 대기열: 3,000~10,000명 동시 오픈에서 응모 API 에 닿는 부하를 초당 배치 수로 제한해 응모 p99 를 30ms 안쪽으로 유지했다. 배치 크기는 대기 시간과 맞바꾸는 손잡이(S5)이며, 이 환경에서는 배치 1,000 까지 응모 API 가 버틴다.
  - D2 "성공 = 발행 확정": 정합성을 지켰고, 측정 범위에서 처리량 상한의 주원인은 아니었다 (Kafka 를 거치지 않는 409 도 같은 수준으로 느려짐, B6). 대기열이 없는 쿠폰 경로는 10,000 동시 이상에서 인스턴스 처리량 상한에 닿는다.
  - Redis AOF: 재시작 후 응모·발급 상태 유지 (S6).
- **이번 단계에서 고친 것**: 업스트림 연결 폭주(P1), gateway OOM(P2), 로그인 커넥션 점유(P3), 서비스 OOM(P4).
- **한계**
  - 단일 머신(k6·서비스·인프라 동거), Docker Desktop 포트 포워딩, 호스트 임시 포트 상한(약 16,000 동시 연결).
  - 콜드 스타트 영향이 커서(B4) 수치가 "얼마나 데운 상태인가" 에 민감하다. 같은 조건 반복 간 p99 편차가 수백 ms 까지 난다.
  - Redis 비정상 종료(kill -9) 실험, DB 락 방식 비교(3.8 선택 과제)는 하지 않았다.
- **다음 개선 과제** (백로그): 쿠폰 처리량 상한(B6 ①~③), 큰 배치에서 입장 후 매진(E-34 관찰 결과 — 정책 재검토는 사용자 결정), gateway 풀 대기 초과 시 500 → 503, gateway 메모리·동시 연결 상한, 배포 직후 워밍업(콜드 스타트), 로그인 처리량(BCrypt) 상한.
